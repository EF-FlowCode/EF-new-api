# 消费余额批量返还

> 定位：现行使用与配置指南。带日期的部署或验证段落保留为当时记录；分类入口见[文档导航](../README.md)。

仅超级管理员（root，role=100）可对选定的历史消费批量返还站内余额。命令行工具和独立财务页面使用同一 API、预览批次及防重记录。返还属于人工批准的消费补偿，不自动认定低输出请求为多扣，也不处理提现。

## 操作入口

超级管理员进入管理后台“财务 → 批量返还余额”，地址为 `/system-settings/maintenance/usage-refunds`。通用日志已移除返还按钮和消费记录勾选，普通管理员、客服和普通用户不能进入该页面或调用返还 API。可选择：

- 在独立页面填写筛选条件：日期、分组、渠道 ID、用户、模型、令牌和请求 ID。默认输出 Token 不超过 1，可关闭该限制。
- 粘贴标识清单或导入 CSV，明确选择日志 ID、本地请求 ID 或上游请求 ID，以及 CSV 中对应的列。
- “手动返还”：用于批量筛选识别不到的个别异常。按用户 ID 或精确用户名、时间范围（最多 31 天）及可选模型、请求 ID 列出该用户的正数消费记录，逐条勾选，每条可按页面显示的货币填写返还金额（如 `0.3`），须大于 0 且不超过原扣费；留空或填写与原扣费显示值相同的金额即全额返还。页面按站点显示货币设置把金额换算成整数额度提交，换算后不足 1 额度或超过原扣费会拒绝提交。列表同时显示已返还记录及其批次，已返还或不可返还的记录不能勾选。
- “异常计费”：审核结算时用量不可靠的消费日志（`logs.billing_anomaly`：1 输入按本地估算、2 仅输出按估算、3 上游未交付任何用量）。按时间（最多 31 天）、类别、用户 ID、渠道 ID、模型查询，可切换“明细”和“按用户汇总”（汇总里点“查看明细”直接筛选该用户）。类别 1、2 已按估算扣费，可勾选后点“转入返还预览”：页面切到“导入清单”、按日志 ID 填好并勾上“包含客户端断开”，填写原因后照常预览、执行。类别 3 已按 0 结算免单，只供审核（发现反复首字前断开的用户或首字超时的渠道），不能勾选。已返还记录显示原批次号。只读接口 `POST /api/log/refunds/anomalies`（RootAuth）。标记从新版本上线后开始写入，此前的历史日志均为 0，不会出现在该 tab。

填写返还原因后预览。预览会显示每人金额、总额、可返还记录及跳过原因；默认排除 `client_gone`，可以显式包含。勾选金额和笔数确认框后执行。批次记录可重新打开、核对到账状态和导出 CSV。

预览默认只显示可返还记录，支持切换“已跳过”和“全部”，并分别显示笔数。“已跳过：客户端已断开”“已跳过：已返还”等记录不计入可返还金额。已返还记录同时显示原返还批次号；全部均不可返还时默认显示跳过清单。

手动返还沿用同一预览、执行和批次流程：预览项目的 `quota` 是本次返还额，`original_quota` 是原扣费；确认框、每人汇总和执行校验都按返还额计算。每条日志仍只能返还一次，部分返还后剩余部分不能再次返还。

仅返还正数消费额度。零扣费、非消费、无法解析的用量元数据、已返还记录、已删除用户或越权用户均不返还。任务与违规独立计费记录仍走原处理流程。筛选范围最多 31 天，每批最多 5000 条，超限会拒绝预览，不能把前 5000 条误当成全部。

预览保存 24 小时有效的固定清单。执行前重新核对原日志；原记录被修改、删除，或被另一批次返还时，整批拒绝执行并要求重新预览。批次只允许创建它的超级管理员查询和执行；账号降为普通管理员后也无法继续操作旧批次。

预览扫描保留 8 秒查询预算，按筛选条件取完整候选后在内存按日志 ID 排序，避免数据库为排序选择全历史主键扫描。预览超时返回 HTTP 504，并提示缩小日期范围或导入请求 ID，预览本身不修改余额；其他预览失败同样明确未修改余额。只有执行返还的结果未能确认时，才要求查询原批次状态后重试。

## 用户可见记录

概览的“账户收支”展示当前余额、累计净消费、消费返还和请求次数，支持整体刷新。消费结算额沿用 `users.used_quota`，自动任务退款已在该值中回减；净消费仅再扣减 `usage_refund_receipts` 中当前用户已到账的批量消费返还，避免自动退款重复扣减。余额和凭证总额通过主库单条 SQL 的同一快照读取，不依赖用户日志补写进度，不修改原始消费、充值或余额。

“退款与返还记录”统一提供三类个人只读明细：消费返还按批次合并、自动退款取历史退款日志并排除已纳入消费返还的批次通知、退款工单展示申请额度和处理状态。工单历史数据不能证明实际外部转账金额，不能据此从消费额再次扣减。自动退款日志受现有日志保留范围影响；此页面不是覆盖赠送、人工余额调整等全部来源的完整资金流水。

个人接口为 `GET /api/user/self/usage-summary` 和 `GET /api/user/self/refund-records?kind=usage|task|ticket&p=1&page_size=10`。均使用现有 `UserAuth`，只以认证身份取当前用户，忽略调用方传入的 `user_id`；不开放批量返还管理权限。汇总包含 `quota`、`used_quota`、`refunded_quota`、`net_used_quota`、`request_count`，单位均为原始额度（请求数除外）。明细返回 `items`、`has_more`，每页最多 100 条、页码 1 至 10000；条目仅含类型、标识、时间、额度、原因、状态及必要的请求/工单引用，不返回收款账号或管理员内部信息。

前端提示净消费与返还的关系，并区分已到账记录与退款申请。跨期消费返还按实际返还时间出现在明细，不回写原消费日期。接口失败显示错误，不能将未加载的返还金额当作零。

每个用户每个成功批次新增一条“余额已返还”日志，包含返还总额、笔数、原因及批次号。用户在自己的“使用日志”中即可查看，管理员内部信息不会暴露给用户。金额按站点货币设置显示；不发送邮件或外部消息。

原消费记录的费用旁显示“已返还”标记，详情显示返还金额和批次号。该标记查询主库返还凭证后补充到当前日志页，不修改原消费金额或日志内容，也无需跨数据库关联。日志 API 的 `usage_refund` 包含 `batch_id`、`quota`、`refunded_at`；返还预览项目通过 `refund_batch_id` 标识已返还记录。再次筛选时自动跳过，数据库唯一约束继续阻止跨批次重复返还。

余额和返还凭证、待写用户日志在主库同一事务提交。日志库可以独立部署：日志写入失败不会撤销已到账余额，而由主节点后台每 30 秒补写（每轮最多 100 条）。页面显示待写入数量；日志库的批次/用户唯一标记避免重复日志。原消费日志保持不变。

## 命令行

工具入口为 `cmd/usage-refund`，只调用超级管理员 API，不直接连接数据库。运行前须取得由项目固定 Go 容器编译、与候选源码匹配并已验收的 Windows 工具 `usage-refund.exe`，放在当前目录；不在宿主机临时 `go run`。必须使用 root 账号的访问令牌，不能用普通管理员令牌或模型调用 API Key；不要把令牌作为命令参数或写进预览清单。

```powershell
$env:NEW_API_URL = 'https://your-new-api.example'
$env:NEW_API_ADMIN_ID = '超级管理员用户ID'
# NEW_API_ADMIN_TOKEN 通过当前终端的安全环境配置提供

# CSV 只取本地消费日志 ID，金额由服务器读取
.\usage-refund.exe preview --csv candidates.csv --column log_id --kind log --reason '9月7日 Responses 中断补偿' --file preview.json

# 改用上游请求 ID 时，选择 --kind upstream 和实际请求 ID 列
# --kind request 表示本地 request_id；上游 usage_log_id 不是本地日志 ID

# 检查 preview.json 后，用预览中的完整批次号确认
.\usage-refund.exe execute --file preview.json --confirm '预览批次号'
.\usage-refund.exe show --id '预览批次号'
.\usage-refund.exe list
```

也可用 `--selection selection.json` 代替 CSV。示例文件：

```json
{
  "reason": "9月7日 Responses 中断补偿",
  "include_client_gone": false,
  "filter": {
    "start_timestamp": 1788710400,
    "end_timestamp": 1788796799,
    "group": "1_vip_codex",
    "channel": 110,
    "max_completion_tokens": 1
  }
}
```

时间戳为秒，示例对应北京时间 2026-09-07 全天。标识清单与 filter 只能选择一种。部分返还在 `--selection` 中写 `"log_ids": [123, 124]` 与 `"amounts": {"123": 5000}`。预览文件绑定服务器和管理员，不含访问令牌；包含用户与请求信息，应按管理资料保存。请求失败后使用 `show` 查询原批次，重复执行同批次不会重复返还。

## API

均需 `RootAuth` 和现有身份头 `New-Api-User`，执行参数不能指定任意用户或退款金额。保留 `/api/log/refunds` 路径以兼容 CLI，但它不是通用日志权限的一部分；四个端点均拒绝非 root 身份，隐藏按钮不能替代服务端权限。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/api/log/refunds/candidates` | 只读：按 `user_id` 或 `username`（二选一，精确匹配）、`start_timestamp`、`end_timestamp`（最多 31 天）、可选 `model_name`、`request_id`、`include_client_gone` 列出该用户正数消费日志及可返还状态、已返还批次与额度；不创建批次，超过 5000 条返回 400 |
| POST | `/api/log/refunds/preview` | 提交 `reason`、`include_client_gone` 和 `log_ids` / `request_ids` / `upstream_request_ids` / `filter` 之一；`log_ids` 模式可附 `amounts`（`{"日志ID": 返还额度}`） |
| GET | `/api/log/refunds/` | 当前管理员最近 50 个批次 |
| GET | `/api/log/refunds/:id` | 固定清单、每人汇总、返还凭证、用户日志待写数量 |
| POST | `/api/log/refunds/:id/execute` | 提交预览的 `expected_quota` 和 `expected_count` |

`quota` 始终是数据库原始整数额度，不是美元或人民币。CSV 中金额字段不参与计算。`amounts` 只能与 `log_ids` 同用，键须出现在 `log_ids` 中，值为原始整数额度（不是金额，页面填写的金额由前端换算），须不小于 1 且不超过该日志原扣费，否则返回 400；未列出的日志按原额返还。预览快照固化返还额，执行时仍重新核对原日志未变、未被其他批次返还，钱包、令牌、返还凭证与用户“余额已返还”日志均按实际返还额记账。成功响应遵循 `{success:true,data:...}`；预览过期或变更为 HTTP 409，参数/超限为 400，批次不存在或非本人为 404。

## 数据与部署

手动返还不新增表或字段。新增主库表 `usage_refund_batches`、`usage_refund_receipts`、`usage_refund_notices`；日志库新增 `usage_refund_log_deliveries`。主库与日志库相同时只在同一库创建一次。通过现有 `MigrateDatabases` 创建，无需对大日志表添加索引或字段。

源消费日志 ID 在返还凭证中永久唯一，跨批次、重启和并发均防重。用户余额与仍属于该用户的有效令牌额度共同返还；令牌已删除时仍返还用户余额。历史消费统计保留原始累计值，返还作为单独记录，不修改渠道成本或历史消费额。

本功能无法自动识别此前在其他工具中直接加余额的人工补偿；有过人工处理的记录应从首次清单排除。用户日志不是弹窗通知，用户需要进入使用日志查看。

## 验证

以下局部检查从仓库根目录用 Git Bash 执行；专用测试 MySQL 的启停按项目授权规则处理，详见[Docker 检查入口](../development/local-development.md#docker-检查入口)。

```shell
scripts/docker-check.sh go-test ./model ./controller -run '^TestUsageRefund' -count=1 -timeout=120s
scripts/docker-check.sh go-test ./cmd/usage-refund -count=1 -timeout=60s
```

Docker 入口自动配置专用测试 DSN，测试 helper 创建并清理随机隔离库。前端用例 `src/features/usage-refunds/lib/refunds.test.ts` 使用[本地开发中的固定 Bun 容器示例](../development/local-development.md#docker-检查入口)执行；页面交互用 Playwright 模拟接口验证，真实金额事务由 MySQL 用例验证。生产迁移、真实返还及部署需另行执行。
